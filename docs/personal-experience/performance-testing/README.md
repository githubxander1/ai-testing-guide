# 性能测试方案与分析

性能测试要回答具体容量或体验问题，结论依赖业务负载、环境和目标指标。先与产品、开发和运维确认目标，再设计负载和观测点；不要直接套用其他项目的并发量或通过线。

## 什么时候介入

- 核心链路、预计流量或数据量明显增长。
- 架构、数据库、缓存、消息队列或部署规格有重要变化。
- 真实用户反馈慢、超时或高峰不稳定，需要基线和定位证据。
- 发布目标包含容量、响应时间、成功率或稳定运行要求。

是否测试及其优先级，按业务影响、流量、风险和变更评估。旧资料中的日调用量、秒数、CPU 百分比和成功率都是特定项目的历史指标，不能直接当行业门槛。

## 开测前要定清楚

| 项目 | 要确认的内容 |
|---|---|
| 目标 | 要验证的用户量、吞吐、响应时间、稳定运行时长或容量边界 |
| 业务场景 | 核心事务、读写比例、请求节奏、思考时间、峰值分布和关键断言 |
| 环境 | 应用、数据库、缓存、依赖服务的规格和配置；与目标环境有哪些差异 |
| 数据 | 数据量、分布、唯一性、准备和清理方式；避免重复数据导致缓存命中失真 |
| 观测 | 客户端、应用、数据库、队列和主机的指标、日志、链路追踪及采集间隔 |
| 安全边界 | 负载工具位置、压测授权、限流保护、停止条件和异常联系人 |

先写下可验收的目标和停止条件。目标值应来自业务约定、SLO 或基线，不从旧报告复制。

## 测试类型怎么选

- **基线测试**：小负载下确认脚本、数据、指标链路和系统行为正确。
- **负载测试**：在预期负载范围内观察响应、吞吐、错误和资源趋势。
- **压力测试**：逐步超过预期负载，观察拐点、降级和恢复行为。
- **峰值测试**：验证短时流量突增、限流和恢复。
- **稳定性测试**：较长时间运行，观察资源增长、错误累积和性能漂移。
- **容量测试**：以明确业务目标寻找可持续承载范围；记录部署规格和业务组合。

## 推荐执行流程

1. 评审目标、范围、模型、环境差异、风险和停止条件。
2. 先做功能校验，确认鉴权、关联参数、数据、断言和清理正确。
3. 用小负载跑通并验证压测机本身没有先成为瓶颈。
4. 逐步升压，记录每个阶段的负载、业务结果和资源变化；达到目标后按约定持续观察。
5. 对比响应时间分位值、吞吐、错误/超时与应用和依赖指标，定位发生变化的时间段。
6. 一次验证一个主要优化假设，保持场景和环境可比较；优化后重跑基线和目标负载。
7. 汇总结论、限制、异常和证据，明确系统在本次条件下是否满足目标。

## 重点指标

- **响应时间**：报告平均值之外的 p50、p90、p95、p99 和最大值，并标清统计窗口。
- **吞吐量**：实际完成的请求或业务事务数/单位时间，同时看成功率，避免把失败请求算成有效能力。
- **并发与到达速率**：区分虚拟用户、在途请求和每秒到达量；三者不能直接互换。
- **错误与超时**：按业务、接口和错误类型拆分，确认是否影响成功事务。
- **资源与依赖**：CPU、内存/GC、磁盘与网络、线程池、连接池、数据库、缓存和队列。
- **业务结果**：数据正确性、重复/丢失、积压和恢复情况。

在稳定窗口内，可用 Little 定律近似理解在途请求数：平均在途请求数 ≈ 吞吐率 × 平均响应时间。它描述请求在系统中的并发量，不等于虚拟用户数；虚拟用户还受思考时间、事务流程和负载模型影响。

## 分析时避免的误区

- 只报平均响应时间，不看长尾和错误率。
- 只看应用 CPU，不看数据库、依赖服务、压测端和网络。
- 以线程数代替真实用户负载，或用日请求量平均分摊代替峰值模型。
- 测试环境与目标环境差异很大，却把结果当作生产容量承诺。
- 运行中修改数据、缓存或配置，导致前后结果不可比较。

## 报告最少包含

目标与通过口径、版本和环境规格、场景与负载曲线、数据准备、工具与脚本、响应分位值/吞吐/错误、资源与依赖表现、问题证据、限制和结论。

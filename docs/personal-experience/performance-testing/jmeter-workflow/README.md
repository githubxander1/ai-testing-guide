# JMeter 实战流程

这页把本地 JMeter 参数化、接口、数据库、监控和命令行笔记整理成一条可复用流程。JMeter 适合按业务事务组织请求和负载；先保证结果可信，再扩大负载。

## 脚本结构

1. **测试计划与变量**：集中管理环境地址、公共参数和线程组设置，环境切换时避免散落修改。
2. **前置配置**：按需设置 HTTP 默认值、请求头、Cookie/鉴权、CSV 数据和计数器。
3. **业务事务**：按真实流程串联请求，处理动态令牌、订单号等关联值。
4. **断言与检查**：检查协议状态、业务码和关键响应字段；只看 HTTP 200 不足以判断业务成功。
5. **结果记录**：保存 JTL 和运行日志；GUI 监听器只用于调试小样本，不在压测运行时收集大量图形结果。

## 参数化与数据

CSV Data Set Config 可将文件行读入变量。上线压测前确认文件编码、分隔符、变量名、EOF 策略、循环方式和线程共享范围；确保数据量足够、唯一性符合场景、不会重复消耗同一账号或业务对象。

动态值要从响应中提取并传给后续请求。遇到接口返回成功但业务数据没有改变时，应检查断言和后置校验，避免把“请求发出”误当成“事务完成”。

## 运行方式

GUI 用于创建和调试脚本；正式负载运行使用命令行模式，便于降低图形界面开销并保存结果文件。示例：

```bash
jmeter -n -t test-plan.jmx -l results.jtl
```

压测前核对 JMeter/Java 版本、线程模型、堆内存、压测机 CPU/网络，以及结果采样配置。不要在 GUI 中长时间跑大负载；脚本出错或机器资源不足时，结果不能代表服务端能力。

## 数据库与主机监控

数据库请求适合用于明确的数据库场景或数据准备验证，不要在不清楚事务和清理影响时直接对业务库加压。服务器监控要覆盖应用和依赖节点，至少能把资源变化与负载阶段、错误和响应时间对齐。

旧笔记中的插件、Agent 下载地址和安装步骤可能已经过期。按当前 JMeter 版本及官方文档选择兼容组件，避免把监控 Agent 暴露到不可信网络。

## 结果复核清单

- 先用少量用户确认请求、参数关联、断言和数据清理正确。
- 结果文件有样本，成功/失败数量与脚本统计一致。
- 关键业务断言通过，异常响应没有被误判成功。
- 线程数、启动时间、持续时间、事务比例与计划一致。
- 压测机和服务端都有足够观测，报告包含版本、环境与负载阶段。

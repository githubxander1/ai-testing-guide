# 需求分析与用例设计

用例设计从需求出发，再用质量和风险视角查缺补漏。先说明“要验证什么、为什么重要”，再选合适的设计方法；模板只是记录载体，不能代替测试分析。

## 从需求到覆盖

1. **澄清规则**：列出角色、状态、输入输出、业务约束、依赖、异常处理和验收口径；把不明确或互相冲突的需求先提出来。
2. **拆解变化点**：标明新增、修改、删除的行为，以及受影响的上下游流程和历史数据。
3. **补质量视角**：按产品需要检查功能正确性、交互与可用性、兼容性、可靠性、性能、安全和数据一致性；不相关的维度不为了凑数而加用例。
4. **选择设计方法**：输入范围适合等价类和边界值；条件组合适合决策表；状态变化适合状态迁移；组合配置多时评估成对组合；复杂流程用场景串联。
5. **复核覆盖**：从需求到用例逐项追踪，确认正常、异常、边界、权限、重复操作、失败恢复和关联影响都按风险考虑过。

## 用例优先级与执行顺序

用例优先级反映风险，不等于执行顺序的永久名单。结合用户影响、发生概率、使用频率、变更范围和依赖故障动态调整：

- 高优先级：核心主流程、关键交易或高影响故障；通常先做冒烟和每轮回归。
- 中优先级：一般业务与常见异常；按版本范围、改动和剩余风险安排。
- 低优先级：低频或影响较小的场景；时间不足时需要记录取舍及风险，不应默认永远跳过。

执行时先确认构建可用，再覆盖核心链路和本次变更，随后按风险扩展回归。优先级应随着缺陷、需求和生产反馈更新。

## 可复用的用例记录

| 字段 | 记录要点 |
|---|---|
| 编号、模块、标题 | 能唯一识别场景，名称描述验证目标 |
| 优先级、需求关联 | 说明风险排序和来源 |
| 前置条件、测试数据 | 写清账号角色、状态、数据和环境要求；公开示例不得放真实凭据 |
| 操作步骤 | 每步可复现，避免把多条无关操作写成一步 |
| 预期结果 | 可观察、可判定，包含关键状态和数据变化 |
| 实际结果、执行状态 | 记录通过、失败、阻塞或未执行及原因 |
| 证据、执行人、时间 | 方便复核；日志和截图按权限保存 |

## 缺陷记录的最低信息

写清版本和环境、前置条件、稳定复现步骤、预期与实际结果、影响范围、复现频率和必要证据。严重问题及时同步；修复后验证原场景及关联回归，并更新缺陷状态。不要把真实账号、令牌、客户信息或内部地址放到公开复盘中。

## 练习

给一个“登录失败后可重试，连续失败会触发限制”的需求，先补问限制规则和恢复条件，再用状态迁移或决策表设计正常、边界、锁定、恢复和重复提交场景。最后按风险标优先级，并写一条可复现的缺陷报告。
